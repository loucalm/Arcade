# game/ — Projet Unity (Kenta)

Base : clone de [anatidae-toolkit](https://github.com/XariusExcl/anatidae-toolkit) (sans son `.git`).
Ouvrir **ce dossier `game/`** dans Unity Hub, avec **exactement Unity 6000.3.23f1** (ADR-008). Ne pas changer de version sans décision d'équipe : ça réécrit `ProjectSettings/` et crée des conflits.
Scène de travail : `Assets/_Project/Scenes/Main.unity`, la seule dans les Build Settings. Plateforme active : **Web**.
Piège : l'ancien 6000.0.40f1 bloque sur « Initialize Package Manager » sur les Mac Apple Silicon sans Rosetta 2. Ne plus l'utiliser.

## Configuration figée (ne pas changer sans ADR)
- **Built-in Render Pipeline** (pas d'URP ni de HDRP). Espace couleur Gamma.
- **Ancien Input Manager** (`activeInputHandler: 0`). Ne pas installer le package Input System.
- Web : gabarit **Kenta** (`Assets/WebGLTemplates/Kenta` : page sans défilement, rendu fixe 1920×1080 quelle que soit la mise à l'échelle de Windows ; ADR-031), build **release** (jamais Development), IL2CPP Release « vitesse », compression **Disabled** (le serveur Express de la borne n'envoie pas les en-têtes gzip/brotli), 1920×1080, data caching activé.
- Mode éditeur par défaut en 3D : on fait de la 2D en sprites et caméra orthographique, sans changer le template.

## Toolkit Anatidae — ce qu'on réutilise
- `HighscoreManager.GameName` → **`"Kenta"`** (`Assets/Anatidae/Scripts/HighscoreManager.cs`). Doit être identique au nom du dossier de build.
- Le prefab **`AnatidaeInterface`** doit être présent dans **chaque scène**. Il contient `MenuManager` (bouton blanc 1,5 s + AFK 60 s), `HighscoreNameInput` et `HighscoreUI`. En build Web, `Core/ArcadeMenu` désactive `MenuManager` au lancement et fait son travail avec `ArcadeInput` (manettes lues dans le navigateur, ADR-029). Les 60 s d'inactivité (et les délais des menus) se comptent sur de vrais gestes (`ArcadeInput.AnyActivity` : bouton pressé, joystick qui change de direction) : un bouton ou un axe bloqué empêchait la sortie sur la borne.
- **Manettes en build Web** : `Plugins/WebGL/KentaGamepad.jslib` + `Core/ArcadePads` (joueur 1 = première manette branchée, haut = +1 comme le menu de la borne). Tester sans borne : servir le build et injecter une fausse manette dans `navigator.getGamepads()` (index ≠ 0 pour reproduire le piège).
- Au démarrage : `HighscoreManager.FetchHighscores()` (dans `GameFlow.FetchScores`), **avant** tout `IsHighscore()`, puis `LevelScores.FetchFromBorne()` si la borne a répondu.
- Fin de partie : si le score entre dans le top 10 de la borne (`HighscoreManager.IsHighscore`) ou du niveau (`LevelScores.IsTopTen`) → **notre** écran `UI/NameEntryScreen` (pixel art), puis `HighscoreManager.SetHighscore(nom, score)` et `LevelScores.Record` (+ `Upload` si la borne répond). Le classement s'affiche avec **notre** `UI/HighscoreBoard` (`ShowOfficial` : `HighscoreManager.Highscores` ; `ShowLevel` : `LevelScores`). L'interface du toolkit (`HighscoreUI`, `HighscoreNameInput`, police Arial) n'est plus montrée (ADR-021) ; ses données et l'envoi restent ceux du toolkit.
- Appels vers notre VPS : **uniquement `AnatidaeProxyWebRequest.Get/Post`**, qui passe par `localhost:3000/proxy`. URL de base dans un ScriptableObject `NetConfig` (en local : `http://localhost:8080/api`). Contrat dans [../docs/api-contract.md](../docs/api-contract.md).
- En éditeur, `Core/EditorArcadeShim` (compilé seulement dans l'éditeur, le toolkit n'est pas modifié) : coupe `MenuManager`, dont `BackToMenu()` (`.jslib`) n'existe qu'en build Web et levait une exception à chaque image après 60 s d'AFK ou Échap maintenu ; à la place, retour à l'écran d'accueil. Il démarre aussi avec un classement vide, marqué récupéré, quand la borne locale (`localhost:3000`) ne répond pas (sinon `HighscoreUI` levait une `NullReferenceException`) : la saisie du nom s'ouvre en fin de partie, mais le score n'est envoyé nulle part. Pour tester le vrai retour au menu et les scores : build + borne locale.
- `TextMesh Pro/.../LiberationSans SDF - Fallback.asset` change tout seul (atlas de police dynamique) : **ne pas le commiter** (`git restore` dessus).
- `ExtradataManager` sert à stocker des clés/valeurs sur la borne : classements par niveau (`top_<id>`, `LevelScores`), plus tard des stats globales (ex. nombre total de morts). `SetExtraData` écrit une erreur en console si la borne ne répond pas : ne l'appeler que si `LevelScores.Online`.

## Flow d'écrans (ADR-007)
Scène unique `Scenes/Main.unity`. `Kenta.Core.GameFlow` est une machine à états : `Attract → Explain → Config (héros) → LevelSelect (niveau) → Playing → GameOver → NameEntry (si top 10) → Attract`. Un prefab par écran dans `Prefabs/Screens/`. Détails : [../docs/game-design.md](../docs/game-design.md).
- Musique des menus (accueil, consignes, héros) : `Song_Menu` (*Behind the waterfall…*, calme) sur `GameFlow.attractSong` ; l'écran des niveaux joue l'extrait du morceau du niveau (ADR-037).
- Attract : entrée façon arcade à chaque retour du logo (`AttractScreen.PlayIntro`, ~2 s) : écran noir, lettres K-E-N-T-A qui tombent une à une (éclair blanc, secousse, son), gros flash qui révèle le décor et illumine le logo, sous-titre écrit lettre par lettre, meilleur score qui glisse, « APPUIE SUR START » qui clignote ; reflet sur le logo toutes les 3 s. Sprites `Gen/ui/logo_letter_*`, `logo_white`, `logo_shine_*` (`gen-kenta-assets.py --only ui`). Pendant la démo : le logo en haut, plus d'étiquette « DÉMO ». Cycle logo (15 s) → démo jouée en autoplay, un niveau différent à chaque fois (20 s) → classement de ce niveau (8 s). N'importe quel bouton lance la partie (et débloque l'audio).
- Config : héros (gauche/droite), avec leur difficulté (FACILE / MOYEN / DUR, ADR-036). Rejouer dans la minute (`GameSession.IsQuickRetry`) saute les consignes et reprend héros et niveau.
- LevelSelect (`UI/LevelSelectScreen`, ADR-032) : liste façon osu! (haut/bas, la liste boucle), décor et extrait du morceau du niveau (`SongData.previewBeat`), top 5 du niveau ; B1 jouer, B2 retour au héros, 15 s. Calculs purs testés : `UI/LevelListLayout`, `UI/StickRepeat`.
- GameOver : panneau puis classement **du niveau joué**, chacun passable au bouton 1 ; si top 10 (du niveau ou de la borne) → saisie du nom → retour à l'accueil sur ce classement (le nouveau score pulse en or).
- **Classements par niveau** : `Core/LevelScores` (top 10, une entrée par nom : la meilleure, avec son héros et sa difficulté, ADR-037), dans l'Extradata de la borne (clé `top_<id>`), lue seulement si `FetchHighscores` a vraiment répondu ; sans borne, en mémoire. La liste officielle (`HighscoreManager`) reçoit aussi chaque score.

## Entrées
- Classe unique `Kenta.Core.ArcadeInput` : lit `P{n}_Horizontal`/`P{n}_Vertical` (dead zone **0,3** sur `GetAxisRaw`) et `P{n}_B1`, `P{n}_B2`, `P{n}_Start`.
- Mapping de jeu : **B1 = saut**, **B2 = frappe**. Plus de glissade (ADR-030) : le joystick ne sert qu'aux menus. Start = valider dans les menus.
- Clavier de dev (P1, AZERTY) : ZQSD, F = B1, G = B2, X = Start, **Échap = bouton blanc**. Voir [../docs/anatidae.md](../docs/anatidae.md).
- Axe vertical manette déjà inversé dans l'InputManager : **haut = positif**.

## Rythme (cœur technique)
- `Conductor` (singleton, `Rhythm/Conductor.cs`) : `SongTime` vient de `timeSamples / frequency`, interpolé avec `unscaledDeltaTime` et recalé à chaque nouveau paquet audio (correction douce, saut au-delà de 20 ms). API : `Play(SongData, startBeat, loop, useRemix)`, `Seek(beat)`, `Stop()`, `SongTime`, `SongBeat`, `BeatToSeconds()` (relatif au beat 0, offset déjà retiré), `OnBeat(int)`, `OnSongEnd`. Il gère les clips en boucle (menu).
- ⚠️ Fin de morceau : une source arrêtée repart à `timeSamples` 0 ; ne jamais recaler le temps sur une source arrêtée (sinon, fin ratée et le niveau recommence : `Conductor.ReachedEnd`). En build Web (la borne), une source peut aussi rester « en lecture » après la fin, position figée : la fin se décide sur le temps du morceau, pas sur `isPlaying` seul (`Conductor.SongEnded`, sinon le héros court dans le vide après la fin ; `ConductorEndTests`).
- Démarrage via `Play()` + `timeSamples`, **pas** `PlayScheduled`/`dspTime` (non garantis sur WebGL).
- Un morceau = un asset `SongData` (`ScriptableObjects/Songs/`) : clip, remixClip, bpm, offsetSeconds, beatsPerBar, chart.
- S'abonner aux événements du Conductor dans `Start()` (pas `OnEnable`), ou en différé comme `FX/BeatPulse` : l'ordre des `Awake` n'est pas garanti.
- Pistes de test générées par `tools/gen-test-beat.py` (kick sur chaque temps) : `Audio/Test/test_*_120.wav`.
- ⚠️ Le navigateur exige une interaction avant de jouer du son. À vérifier **sur la borne** (l'appui sur un bouton de manette compte-t-il ?). Attract = « APPUIE SUR UN BOUTON », et ce premier appui débloque l'audio.
- `LevelBuilder` : lit la chart JSON (`Charts/*.json` via `TextAsset`) et instancie les prefabs à `x = BeatToSeconds(beat) * runSpeed`. Pooling obligatoire.
- `ActionSfx` : quantifie les sons d'action à la double-croche (`round(beat * 4) / 4`). Exception, la note d'une pièce (`LumNote(note, beat)`) : elle sonne sur le temps de la pièce (`PlayDelayed`, 2 temps d'avance au plus), car on la ramasse ~0,3 temps avant ; quantifiée, elle sonnait une double-croche trop tôt.
- ⚠️ Le jeu et le simulateur doivent rester identiques (`levelgen/engine.py` ↔ `PlayerController`, `LevelBuilder`). Écarts déjà trouvés : sol ramené à 60 u (`LevelBuilder.MaxHeight`, maintenant 200 u et vérifié par le générateur) ; portail de gravité à une image de l'atterrissage (`LandBeforeFlip`). Pour en chercher un : autoplay dans le jeu, liste des pièces restées `alive`, trajectoire comparée à celle du simulateur.
- Notes de saut : un appui jusqu'à 0,3 temps avant la fenêtre (±0,35 temps) est gardé et part à l'ouverture ; un appui ne sert qu'à une note (`PlayerController.CheckOrbs`, `OrbMemoryBeats` ; `ORB_MEMORY` dans `levelgen/engine.py`). Avant, un appui un peu tôt était ignoré et on tombait.
- Lianes : un appui après la prise, même en avance, est gardé ; on lâche à l'ouverture de la fenêtre (±0,35 temps autour du temps de la liane), jamais ignoré (`PlayerController.Swing`, même règle dans `levelgen/engine.py`).
- Pièces : sur la grille des croches, ramassées dans un rayon de **1 u** (`PlayerController.pickupRadius`, le même que `PICKUP` du simulateur `levelgen/engine.py` : à changer des deux côtés), dans le calque des acteurs comme le héros (elles gardent leur or quand le monde passe en négatif, niveau 9 ; celles de l'arrière-plan restent dans le calque du monde), avec un petit saut de 6 px (`FX/CoinPickup` ; ⚠️ ne rien remettre à zéro dans son `OnEnable` : `Play()` active le composant, l'animation était annulée et les pièces ramassées restaient affichées). Règles de placement : `docs/level-design-musical.md`.
- Clips musicaux : Vorbis, `Compressed In Memory`, `Preload Audio Data` activé. SFX courts : `Decompress On Load`.

## Gameplay et DA Kenta (voir [../docs/art-direction.md](../docs/art-direction.md))
Le jeu est en **pixel art agrandi d'un facteur entier** : vue du monde de 320 à 640 px de large selon le plan de caméra, interface en 320 × 180 ×6 (ADR-018 ; 3 calques : monde, acteurs, interface ; défilement au sous-pixel, voir docs/art-direction.md). Monde : 40 px/unité. Hitbox héros 0,5 × 1,0 u, saut 1,5 u en 1 beat, vitesse 8 u/s. Die and retry selon le héros (ADR-036) : Kenta 10 vies et reprise au dernier point, Aiko 3 essais et reprise au début (le meilleur compte), Ryo une seule vie.

## Juice / perfs (GPU intégré)
- Cible **60 fps** en build Web sur la borne. Pas de post-process plein écran coûteux, pas d'ombres, peu de lumières.
- Juice = secousses en pixels entiers, flash des drops, particules en pixels (< ~300 actives). **Pas d'animation par crans sur le beat** (lu comme un tremblement) : mouvements continus ou cycles d'images.
- Sprites pixel art : filtre Point, aucune compression (réglé par `KentaSpritePostprocessor`).
- ⚠️ Piège : un sprite créé en code (`Sprite.Create`, ex. dégradé de 1 × 8 px) a la taille de sa texture divisée par son PPU ; pour couvrir la vue, diviser l'échelle par `sprite.bounds.size` (la brume du décor ne couvrait qu'une colonne au centre).
- ⚠️ Jamais d'effet de bord dans l'argument d'un appel `?.` (`Event?.Invoke(list[i++])`) : sans abonné, l'argument n'est pas évalué. Une boucle de `RunManager.Update` ne faisait plus avancer son curseur et figeait Unity à 100 % (27/11).
- Pas d'allocation dans `Update` (pas de LINQ ni de `new` par frame) : le GC WebGL provoque des saccades. Un texte qui change (score) : ne refaire la chaîne que si la valeur change.
- **Niveau par tranches** (`LevelBuilder.BuildChunks`) : les objets sont rangés par tranches de 8 u, seules celles autour de la caméra sont actives (≈ 560 sprites actifs au lieu de 6 000). Un objet ramassé ou tué (`activeSelf` faux) le reste. Un nouvel objet de niveau doit être un enfant d'un groupe du niveau (il sera rangé tout seul) ; plus large que 12 u, il reste toujours actif.
- **Physique du héros en pas de 1/60 s** (`PlayerController.Update` → `Step`) : une image longue (lag, GC) est rejouée en petits pas, comme le simulateur du générateur. Sans ça, sur la borne : morts sur les rampes raides et dans les cuirassés. La manette est lue une fois par image (appui au dernier pas), l'autoplay à chaque pas.
- ⚠️ Piège : chaque « Reconstruire » ajoutait un `World/Bandana` de plus (30 dans la scène, ~1 400 sprites en fin de partie). Corrigé dans `KentaBuilder` ; vérifier `grep -c "m_Name: Bandana$" Main.unity` = 1.
- Outils de mesure locaux (non commités, dans `Scripts/Editor/`) : partie en lag simulé (15 i/s + à-coups), sonde d'objets actifs et d'allocations. En éditeur, ~12 Ko/image sont alloués par l'éditeur lui-même (même à l'accueil) : ne pas les attribuer au jeu.

## Debug
- `Debug/` (namespace **`Kenta.DebugTools`**, jamais `.Debug`, qui masquerait `UnityEngine.Debug`) : `RhythmDebugOverlay` affiche état, temps, beat, dérive et fps, avec un carré qui flashe sur le beat. Visible en éditeur et en Development Build, **F9** pour basculer (F1 ouvre l'aide de Firefox). Avec l'overlay affiché : **F10 = autoplay** pour valider une chart. Les repères de rythme (un trait par temps, plus marqué sur le 1er temps de la mesure) ne sont plus du debug : `FX/BeatGuides` les affiche toujours, et ils suivent la caméra en hauteur.
- `GameFlow` (`Core/GameFlow.cs`) : les écrans sont des prefabs `Prefabs/Screens/Screen_*.prefab` sous le canvas `Screens` (sortingOrder −10, sous l'overlay Anatidae). En attendant le gameplay : +10 points par beat, **Start = fin de partie**.

- **Tests** : Unity Test Framework, tests EditMode sans asmdef dans `Assets/_Project/Editor/Tests/` (MCP `run_tests`, mode EditMode). Tests Python des générateurs : `pytest tools/tests`.
- ⚠️ Piège MCP : `manage_camera screenshot` recompose mal les calques pixel (image fausse). Pour voir le vrai rendu : `ScreenCapture.CaptureScreenshot("Temp/gv.png")` via `execute_code`, puis lire le fichier.
- Hors 1920×1080 (Game view « Free Aspect » ; en build, le gabarit rend toujours en 1920×1080), `PixelScreen` agrandit tout le cadre pour remplir l'écran et calcule l'agrandissement de l'interface sur le cadre (ADR-033) : plus d'interface rognée. Pixels un peu inégaux dans ce cas : pour juger la netteté, Game view en 1920×1080.
- ⚠️ Piège : une capture d'écran (`ScreenCapture`) fige l'éditeur ~100 ms ; une par seconde pendant l'autoplay suffit à faire rater un saut (mort au beat ~48). Pour juger une chart, pas de capture pendant la partie.
- ⚠️ Unity qui sature puis plante : scripts recompilés **pendant le Play mode** (fichier changé sur le disque : `git pull`, fusion, modification). Les tableaux et singletons créés à l'exécution sont perdus, d'où une `NullReferenceException` à chaque image (88 000 dans le journal le 2026-11-27). Réglage conseillé : Preferences > General > Script Changes While Playing = **Recompile After Finished Playing**. Garde-fous dans `FxPool`, `BiomeBackdrop`, `RunManager` (le jeu se fige au lieu de noyer la console).
- ⚠️ Piège MCP : chaque `execute_code` compile du C# dans l'éditeur et fige le jeu ~300 ms (`dt` = 0,333). Pendant une partie en autoplay, ça fait rater un saut. Pour valider une chart : lancer l'autoplay, **ne rien appeler** pendant la durée du morceau, puis lire le résultat une seule fois. Même chose pour les captures (`manage_camera screenshot`) et les gros calculs CPU (génération de sprites).

## Build → borne
1. Menu **Kenta > Build Web (borne)** (`Editor/KentaWebBuild`) : applique les réglages de la borne (gabarit Kenta, release, IL2CPP vitesse) et construit dans **`game/Build`** (gitignoré). Équivaut à File > Build Profiles > Web > Build, **Development Build décoché**, après le menu Kenta > Régler le projet pour la borne (Web). Le module Web doit être installé pour Unity **6000.3.23f1**.
2. `tools/package-build.sh` : copie vers `dist/Kenta/`, ajoute `BuildExtras/{info.json,thumbnail.png,attract.mp4?}` et installe le tout dans la borne locale.
3. `cd tools/anatidae-arcade && node server.js` → `http://localhost:3000`. Le jeu apparaît dans le menu (Entrée/B1 pour lancer). Accès direct : `http://localhost:3000/Kenta/`.
4. Vérifier : **Échap maintenu 1,5 s → retour menu** (testé OK le 2026-09-25), AFK 60 s → menu, `GET /api/?game=Kenta` en 200, saisie du highscore, dead zone, 60 fps.
`game/BuildExtras/thumbnail.png` est générée : `python3 tools/gen-kenta-assets.py --only thumbnail` (la Sylve, Kenta en marionnette, le logo et un bandeau rouge « EN DEV » : retirer l'appel à `demo_banner` dans `gen_thumbnail` pour la version finale). `info.json` le dit aussi (« En développement. » en tête de la description, « (en dev) » dans la phrase d'accroche).

## MCP Unity
Package `com.coplaydev.unity-mcp` **figé en `#v10.2.0`** dans `Packages/manifest.json`. On ne pointe jamais sur `#main` : les 3 postes doivent avoir la même version. Pour monter de version, mettre à jour le manifest et la version du serveur MCP dans la même PR.
Quand il est connecté, s'en servir pour : créer et modifier GameObjects, prefabs et composants, lire la console après compilation, lancer le Play mode. Toujours vérifier la console (0 erreur) avant de rendre la main.
Sans MCP : écrire le C# et lister les étapes éditeur. **Jamais** de modification manuelle des fichiers YAML (`.unity`, `.prefab`, `.asset`, `.meta`).
